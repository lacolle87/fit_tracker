# Fit Tracker

Локальный трекер питания, веса и активности: CLI + веб-дашборд на DuckDB. Без облаков, аккаунтов и телеметрии — все данные живут в одном файле `fit.duckdb` на твоей машине.

Проект создан для персонального контроля состава тела (дефицит калорий, белок, шаги, силовые) и рассчитан на работу в связке с AI-ассистентом: человек диктует «что съел», ассистент пишет в базу и ведёт аналитику. Но всё работает и руками через CLI.

---

## 1. Быстрый старт

Требуется Python 3.10+.

```bash
python -m pip install -r requirements.txt   # duckdb
python fit_tracker.py init                  # создать fit.duckdb со схемой и стартовыми продуктами
python fit_tracker.py log "яйцо 120; рис вареный 150; овощи свежие 200"
python fit_tracker.py today                 # итог дня: калории, Б/Ж/У, приёмы пищи
```

Вес всегда в граммах, строка парсится по разделителям `;`, суффикс `г/гр` можно опускать. Повторные `log` в течение дня добавляются, `today` пересчитывает всё.

---

## 2. Зачем такая архитектура

| Решение | Почему |
|---|---|
| **DuckDB в одном файле** | вся история (питание, вес, активность) — аналитические запросы SQL без сервера; бэкап = скопировать файл |
| **База не в git** | личные данные не должны покидать машину; в репозитории только код и схема |
| **CLI как единственный способ записи** | ассистент и человек пишут в базу одинаково; нет рассинхрона «ручных правок» |
| **Цели — таблица с историей** (`nutrition_targets`) | калории меняются со временем; старые дни считаются против целей той эпохи |
| **Дашборд = локальный HTTP + статичный HTML** | нет сборки, нет зависимостей фронтенда, тесты гоняют реальный сервер |
| **`db_query.py` read-only** | безопасно давать ассистенту/скриптам SQL-доступ на чтение, не рискуя данными |

## 3. Структура проекта

```
fit/
├── fit_tracker.py      # CLI: все команды записи и отчётов (argparse)
├── db.py               # подключение к fit.duckdb, схема, init, логика записи
├── nutrition.py        # парсер строки "название 200; ..." и форматтеры чисел
├── barcode.py          # поиск продукта по штрихкоду (OpenFoodFacts)
├── db_query.py         # read-only SQL-хелпер для запросов к базе
├── dashboard.py        # локальный веб-сервер дашборда (порт 8765)
├── db/
│   ├── schema.sql      # все таблицы
│   └── seed.sql        # стартовые продукты для новой базы
├── web/
│   ├── dashboard.html  # страница дашборда (Tailwind + ApexCharts)
│   └── dashboard.sql   # SQL-запросы, которыми дашборд читает данные
├── assets/             # иконки приложения
├── tests/              # контрактные тесты дашборда (ThreadingHTTPServer)
├── docs/
│   ├── PROMPT.md       # правила работы ассистента с этим трекером
│   └── fit-tracker-skill-reference.md  # приватные заметки (в git не входит)
└── start_dashboard.bat # запуск дашборда с рабочего стола (Windows)
```

Модули импортируют друг друга из корня: `fit_tracker.py` → `db.py` → `nutrition.py`; `dashboard.py` → `db.py` + `barcode.py`. Поэтому код лежит в корне, а «некод» разложен по папкам.

## 4. Как устроены данные

`fit.duckdb` — аналитическая БД, 13 таблиц. Ключевые связи:

```
foods (продукты, БЖУ на 100 г) ──┐
                                 ├──> meals (food_id, grams, meal_type)  ──> дневные итоги
dishes (блюда: партия + БЖУ) ────┘
weights / body_measurements          профиль и история веса
daily_activity (шаги) · workouts (тренировки)
supplements / supplement_intake      БАДы: справочник + журнал
nutrition_targets                    цели калорий/БЖУ с периодами действия
profile                              рост, пол, текущий вес
```

**Главная механика расчёта БЖУ приёма пищи** (реализована в `db.py` и `web/dashboard.sql`):

- `meals.food_id > 0` → это продукт из `foods`: БЖУ = `kcal_100 * grams / 100`
- `meals.food_id < 0` → это блюдо из `dishes` (его id = `-food_id`): БЖУ = `total * grams / total_grams`

Блюда (`dishes`) хранят массу и БЖУ **всей приготовленной партии** — порции логируются долями (`log-dish`), пересчёт автоматический.

**БАДы и лекарства** живут отдельно (`supplements` — справочник с дозами, `supplement_intake` — журнал приёма) и **никогда не включаются** в калории и БЖУ.

## 5. Типовые сценарии работы

**Записать еду** (обычный цикл):

```bash
python fit_tracker.py log "творог 150; яблоко 180" --meal-type breakfast
python fit_tracker.py today            # показать день и отклонение от целей
```

**Новый продукт** — сначала поиск в базе, потом добавление с этикетки (значения на 100 г):

```bash
python fit_tracker.py add-food "Масдам" 350 23 27 0
```

Для круп и макарон уточняй: вес указан **сухого** или **готового** продукта — это меняет расчёт в разы.

**Готовое блюдо** (сварил кастрюлю):

```bash
python fit_tracker.py add-dish "Плов постный" 850 1360 25 47 212   # вся партия
python fit_tracker.py log-dish "Плов постный" 0.3 --meal-type lunch # 30% партии
```

**Вес и состав тела** (обновляет и текущий вес в профиле):

```bash
python fit_tracker.py log-measurement 90.7 25.1 60.9        # вес, %жира, %мышцы
```

**Активность и БАДы:**

```bash
python fit_tracker.py log-steps 12000
python fit_tracker.py log-workout "силовая" 60 --intensity "силовая" --note "жим 3x5 80кг"
python fit_tracker.py log-supplement "Омега-3"            # доза по умолчанию из справочника
```

**Цели** (с историей — старые дни остаются против своих целей):

```bash
python fit_tracker.py set-targets 1770 105 70 180
```

## 6. Запуск UI (дашборд)

Дашборд — локальный веб-сервер + одна HTML-страница. Данные читает напрямую из `fit.duckdb`, ничего никуда не отправляет.

**Вариант 1 — вручную:**

```bash
python dashboard.py
# затем открой http://127.0.0.1:8765
```

**Вариант 2 — с рабочего стола (Windows):**

Запусти `start_dashboard.bat` (или ярлык на него): скрипт убивает зависший старый сервер на порту 8765, поднимает новый и открывает страницу. При закрытии вкладки браузера сервер завершается сам.

**Что внутри:** калории дня и лимит; факт/цель по Б/Ж/У (полоски + донат); приёмы пищи по категориям с удалением; шаги, тренировки за 30 дней; последний замер (вес/%жир/%мышцы); график веса с целевой линией; недельная скорость снижения (кг/нед); средние за 7/30 дней; дневные графики БЖУ, калорий и шагов; поиск по штрихкоду EAN с камеры телефона.

Целевой вес и цель недельного темпа — константы в `web/dashboard.html` (секция графиков веса).

## 7. Разработка

```bash
python -m flake8 .                                    # стиль (конфиг в .flake8)
python -m py_compile fit_tracker.py db.py nutrition.py
python -m unittest discover -s tests                  # контрактные тесты дашборда
```

Тесты (`tests/test_dashboard.py`) поднимают настоящий `ThreadingHTTPServer` с временной базой и проверяют контракт `/api/dashboard` и `/api/meals`, а также что HTML и API говорят об одном и том же формате приёмов пищи.

**Перед каждым коммитом обязательно** flake8 + py_compile (историческое правило проекта — см. `docs/PROMPT.md`).

Git используется локально; сетевые операции (push, публикация) — только по явному решению владельца. Файл `fit.duckdb` в git не попадает (см. `.gitignore`).

## 8. Онбординг для AI-ассистента (прочитай при первом запуске)

Если ты агент, работающий с этим трекером через пользователя:

1. **Источник истины — база, не память.** Профиль: `profile`; цели: `nutrition_targets` (актуальная — по `valid_from`/`valid_to`); продукты и блюда: `foods`/`dishes`. Не дублируй значения в ответах, если их можно взять из базы, и не хардкодь их в коде.
2. **Новый продукт — сначала ищи в базе** (`db_query.py foods <подстрока>`), потом спрашивай у пользователя данные с упаковки и добавляй. В интернет без необходимости не ходи.
3. **Всё съеденное — в `meals`** через `fit_tracker.py log`. После записи показывай: продукт, вес, ккал, Б/Ж/У и остаток до целей дня.
4. **Уточняй сухой/готовый вес** для круп, макарон, бобовых — ошибка в 2–3 раза меняет весь день.
5. **БАДы** — в `supplement_intake`, дозы из `supplements.default_amount/default_unit`; в калории не включать. **Лекарства не назначать и дозировки не менять** — только фиксировать сказанное пользователем и советовать свериться с инструкцией/врачом.
6. **Вес анализируй по тренду**: 7-дневное скользящее среднее, никаких выводов по одному замеру. Первую корректировку целей — после ≥14 дней наблюдений, менять малыми шагами и не чаще раза в 2 недели. **Темп не более 1 кг/нед — верхняя граница.** ML — только после накопления данных, сначала прозрачная статистика.
7. **Калории тренировок не прибавляй** к доступному рациону автоматически.
8. **Жидкость**: обычную воду/чай/кофе не требуй логировать; учитывай сахар, молоко, соки, сладкие напитки, алкоголь.
9. **Технические ловушки** (Windows):
   - работай через venv-питон: `.\.venv\Scripts\python.exe` — в системном Python нет duckdb;
   - кириллица в PowerShell-консоли ломается — читай/пиши файлы через Python-скрипты с `encoding="utf-8"`, командные аргументы кириллицей работают, here-string и пайпы — нет;
   - `db_query.py` открывает базу в **read-only** — правки только через `fit_tracker.py` или отдельный скрипт на запись;
   - после правок кода — flake8 + py_compile перед коммитом.
10. Полные правила работы — `docs/PROMPT.md`.

---

## 9. Принципы

- **Локальность**: данные только на твоей машине, бэкап — копирование одного файла.
- **Прозрачность**: простая схема, читаемый CLI, статичный дашборд без сборки.
- **Осторожность**: цели корректируются по многодневной динамике, а не по одному замеру; никаких автоматических «доеданий» после тренировок.
